Ты фулстак Java spring Angular разработчик, которому нужно дописать проект, который находится в текущем репозитории. Твоя задача- достигнуть соответствия требованиям самым оптимальным и простым путем.

###ЭТАП 1
Под сервисом понимается штука, которая разрабатывается и запускается отдельно от всех остальных сервисов (обычно в отдельном процессе). Если приводить пример на .Net, то сервис - это отдельное ASP.NET-приложение. На UML это называется компонентом. Общение между сервисами может быть только по сети (нельзя вызывать напрямую метод класса из соседнего сервиса). Взаимодействие по сети - это не обязательно взаимодействие между разными машинами. Можно запускать сервисы на одной машине и обращаться друг к другу по url. Это тоже взаимодействие по сети. В данном случае сеть ограничена одной машиной.

Для хранения данных необходимо использовать реляционную СУБД (PostgreSQL или аналогичные). В дополнении к ней можно использовать и другие хранилища (например, Redis), но не для постоянного хранения данных, а для вспомогательных функций (хранение кеша, обмен данными и т.п.). Каждая реляционная БД привязана к своему сервису. Сервис не имеет права лезть в базу чужого сервиса. Если сервису нужны данные из базы соседнего сервиса, он должен за этими данными обратиться именно к API другого сервиса. При этом может случиться так, что у некоторых сервисов не будет своей БД.

Набор обязательных сервисов:
1) Ядро - сервис, который хранит внутри себя все счета клиентов, их баланс, историю всех операций. Не имеет графического интерфейса. (Технический интерфейс можно сделать для отладки и демонстрации)
2) Веб-приложение (или мобильное приложение) клиента банка. Даёт возможность посмотреть информацию о счетах одного клиента. Открыть новый счет или закрыть старый.
3) Веб-приложение (или мобильное приложение) сотрудника банка.

Дает возможность посмотреть все счета всех клиентов и все данные по счетам. Управлять списками клиентов или сотрудников.
4) Сервис выдачи кредитов. Внутренний сервис, определяющий правила взятия кредита и последующего списания оплаты кредита. Не имеет графического интерфейса. (Технический интерфейс можно сделать для отладки и демонстрации)
5) Сервис с информацией о пользователях.


На усмотрение команды могут быть добавлены дополнительные сервисы.

Реализация будет состоять из 3 этапов. Каждый этап сдаётся отдельно.

Этап 1
Рассчитан на 2 недели. 1 марта делаете последний коммит в репозиторий. На неделе с 2 по 8 марта производится сдача того коммита, который был зафиксирован до 1 марта включительно. Возможен индивидуальный перенос сроков сдачи на следующую неделю.

Функциональные требования:

1) Клиент
   a. Может открыть счет в банке (счетов может быть несколько)
   b. Может закрыть счет в банке
   c. Может взять кредит
   d. Может погасить кредит
   e. Может внести деньги на счет (просто кнопочкой)
   f. Может снять деньги со счета (просто кнопочкой)
   g. Может посмотреть историю операций по счету

2) Сотрудник
   a. Может посмотреть все счета всех клиентов
   b. Может посмотреть по каждому счету историю операций
   c. Может создать новый тариф для кредита, указав название и процентную ставку. Для простоты тестирования считаем, что оплата кредита происходит автоматически не раз в месяц, а раз в день (или в минуту).
   d. Может создавать и блокировать новых сотрудников и клиентов
   e. Может посмотреть список кредитов по любому клиенту и детальную информацию по каждому кредиту.

Также требуется предоставить диаграмму компонентов на UML.

Условия задачи могут меняться с течением времени. Причем иногда они могут меняться так, что вам придётся переписать существенную часть того, что вы уже сделали. Это "нормальная" практика из жизни.

Оценка ставится субъективно (не по заранее подготовленной шкале). Однако она будет основана на следующих характеристиках:
1) Качество реализации своего сервиса (или сервисов, если у человека их будет больше одного)
2) Качество интеграций с другими сервисами
3) Понимание написанного и грамотная презентация (под презентацией понимается устный рассказ и демонстрация работы приложения)
4) Бонус за нестандартную архитектуру (например, CQRS, EDA и т.п.)

Технические рекомендации:
1) Разные сервисы можно писать на разных языках программирования. Однако в большинстве случаев удобнее придерживаться одного языка.
2) Все сервисы рекомендуется хранить в одном репозитории, в одном решении (solution).
3) Каждый участник команды при локальной разработке сразу запускает у себя все сервисы, но работает только над одним. (Например, в VisualStudio есть возможность в решении настроить несколько запускаемых проектов)
4) Способы взаимодействия между сервисами определяет сама команда. Между разными сервисами могут быть разные протоколы. Единственное ограничение - взаимодействие должно проходить по сети (в том числе по сети в рамках одного компьютера)
5) Используйте один репозиторий на всю команду. Ведите разработку в разных ветках, а в master (main) фиксируйте основные (релизные) версии своих сервисов.
6) Разворачивание сервисов в docker-контейнерах может быть удобным и функциональным. Однако рекомендую заранее убедиться, что у каждого участника команды достаточно навыков и железа, чтобы работать с докером. Возможно, будет проще от него отказаться.
7) Использование облачного сервера (например, Яндекс.Облака) для публикации релизных версий сервиса может быть удобным решением. Однако заранее оцените возможности вашей команды. Возможно, что это станет блокирующим риском.
###ЭТАП 2
1) Аутентификация должна быть реализована по принципу SSO (Single Sign On). Согласно этому принципу в какие бы приложения (сервисы) не входил пользователь, он использует один и тот же аккаунт. Например, пользователь может войти одновременно и в клиентское приложение, и в приложение сотрудника (да, один человек может быть и сотрудником и клиентом одновременно). Какой именно протокол аутентификации выбрать - решаете вы сами. Рекомендуется начать изучение с OAuth 2.0

Важное требование - логин и пароль пользователь вводит на одной единственной странице, которая никак не связана ни с клиентским приложением, ни с приложением сотрудников. Цель - ни один сервис, кроме сервиса аутентификации, не должен иметь доступа к паролю ни на каком из этапов. В том числе мобильные приложения не должны допускать ввода пароля на своей стороне. Они должны перенаправлять на страницу сервиса аутентификации.

Для проектов на ASP.NET рекомендуется посмотреть на IdentityServer.

2) Все запросы от пользователя должны проходить авторизацию: т.е. мы должны перепроверять, имеет ли пользователь право на конкретно это действие (под действием в том числе понимается просмотр данных).Авторизация должна быть в каждом сервисе, в том числе при запросах между сервисами.

3) Клиент может перевести деньги со счета на счет. Как между своими счетами, так и на чужой счет.

4) Клиентское приложение и приложение сотрудника должно получать список операций по счету с сервера через WebSockets. В том числе этот список должен обновляться в реальном времени. Если была создана новая операция, она сразу должна появиться в приложении. Подумайте, какой паттерн взаимодействия с сервером по ws лучше выбрать: push full data или push invalidation для обновления в реальном времени. 5) Добавление новых операций по счету должно проходить через очередь сообщений (брокер сообщений). Конкретный брокер выбираете вы сами. Это может быть Kafka или любой другой. При этом операции всё равно сохраняются в реляционную БД. Цель - ни при каких обстоятельствах не потерять ни одной операции. Информация об операции сначала записывается в очередь сообщений, а затем оттуда читается ядром, обрабатывается и складывается в БД.

6) На счету ни при каких обстоятельствах не должно оказаться отрицательного баланса.

7) У сотрудников и клиентов должна быть возможность посмотреть, какие платежи по кредиту клиент просрочил. А также посмотреть кредитный рейтинг. Кредитный рейтинг показывает, насколько вероятно человек вернёт следующий кредит. Функцию кредитного рейтинга можете придумать самостоятельно, это не принципиально.

8) В приложении клиента и сотрудника должна быть возможность выбрать тему (темная или светлая), а также отметить некоторые счета скрытыми. При этом тема и скрытые счета сохраняются на уровне приложения (а не на уровне ядра). Но при установке нового экземпляра приложения на новом устройстве у того же пользователя должны загружаться использованные ранее настройки. Это означает, что настройки должны храниться на серверной части приложения. Это означает, что у каждого клиентского приложения должна появиться серверная часть, которая предназначена исключительно для нужд приложения, а не для обработки основных бизнес-процессов банка.

9) Банк не может выдать безграничное количество кредитов. Эмулируем это поведение с помощью мастер-счета. Мастер-счет - это обычный банковский счет, который принадлежит банку. Когда клиент берёт кредит, то деньги с мастер-счета переводятся на счет клиента. При этом на мастер-счет также накладывается правило, что на нём, как и на любом другом счете, ни при каких условиях не должно быть отрицательного баланса.

10) Банк должен поддерживать минимум три валюты. Клиент должен иметь возможность перевести свои деньги со счета в одной валюте на счет в другой валюте. При этом должна произойти конвертация валюты по текущему курсу. Курс валют брать по API из открытых источников в интернете.

11) фронтовое приложение состоит минимум из 3х слоёв:

    UI
    бизнес-логика (use-cases/сценарии)
    слой взаимодействия с сервером

при этом слой взаимодействия с сервером должен быть разделён на два слоя: сетевой слой, который содержит в себе (инкапсулирует) всю логику работы с запросами по сети; а также слой, который содержит бизнес-логику отправки запросов и обработки ответов.
слои не смешиваются (UI не делает fetch напрямую, сетевой слой не знает про UI и т.д.)
В UI слое должен быть выделен слой переиспользуемых компонентов, которые не зависят от конкретных страниц и бизнес-сценариев.
Повторяющиеся паттерны UI (модалки, подтверждения, формы, таблицы) должны использовать общие базовые компоненты/обёртки/конфигурирование, а не копипаст.

12) На фронтенде  должен быть единый механизм обработки ошибок в виде иерархии/конвейера, где ошибки обрабатываются на подходящем уровне (компонент/страница/глобальный обработчик и тд), а необработанные приводят к fallback-странице.

13) На стороне фронтенда должен быть типобезопасный контракт взаимодействия с сервером: DTO запросов/ответов должны быть строго типизированы, использование any (и аналогичных обходных путей типизации) запрещено. Должен быть выбран и обоснован подход, обеспечивающий согласованность контрактов клиента и сервера. Подумайте, какие есть варианты удовлетворения данному требованию.
14) Любое пользовательское действие в интерфейсе должно иметь явную реакцию приложения: отображение статуса выполнения (например, загрузка/ожидание), успешное завершение или сообщение об ошибке. Запрещены “тихие” ошибки, когда пользователь не понимает, произошло ли действие. Подумайте о единообразном механизме отображения состояний и уведомлений.
